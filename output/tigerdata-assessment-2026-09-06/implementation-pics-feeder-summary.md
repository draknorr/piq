## Behavior and limits

`PICS_SUCCESSOR_FEEDER_ENABLED` defaults to false. In durable mode, after live claims and the shared heavy-phase gate, the existing worker calls `ops.feed_pics_successor_backlog` once per processing pass. It admits no more than the catch-up allocation, capped at 100, into a window twice that size, capped at 200. At the proposed initial allocation this is 10 admitted / 20 open. Pending work, delayed retries and owned catch-up all consume the window. A zero quota or shadow mode makes no admission call.

The SQL takes locks in the existing manual-enqueue order (shared heavy gate → try primary intake → successor row). It yields to waiting live work, heavy refreshes, intake contention, operator locks and the persistent pause. It delegates actual row linkage to the reviewed successor enqueue function, preserving before-images, source watermarks, tokens and old audits. Durable item links make restart or an unobserved commit safe without replaying the entire catalog. Admission failure skips catch-up in that pass and preserves already owned live processing.

`last_processing_recovery_feed` exposes admission status, run ID and relevant counts. `manifest_admitted` only means all manifest members have work links; it never declares successful recovery. Terminal linked failures are not silently retried. New history gaps, unavailable access tokens and final audit dispositions remain explicit. There is one collector and Steam governor, with existing request spacing/concurrency limits.

- On the same ten members, alternating manual/automatic order over 20 calls each, median admission was **2.579 ms manual / 2.515 ms automatic**. Median WAL was **27,792 / 27,416 bytes**. This fixture opens a fresh local connection per call; it is not a pooled production latency measurement. Settlements were simulated to isolate admission progress, not collected from Steam. The loop's 93,499,512 WAL bytes include deliberately repeated simulated settlement updates and must not be used as an ingestion WAL forecast.
- The candidate and compatible rollback both pass the latest actual SQL successor lifecycle. The rollback image retains its 161-test evidence and does not include an automatic feeder. Both preserve successor pause and current-run audit scoping.
